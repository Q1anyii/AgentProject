## Q1: 本项目为什么选择 MySQL + PostgreSQL + Redis 三种数据库？能不能只用一种？

**A:**

**三种数据库的职责**：

| 数据库 | 用途 | 选择原因 |
|--------|------|----------|
| MySQL | 用户信息、文件上传、扩展配置 | 结构化业务数据，事务支持，团队熟悉 |
| PostgreSQL | LangGraph Checkpointer + Store | LangGraph 官方原生支持，JSONB 适合图状态 |
| Redis | 检索缓存、JWT 登录态、限流 | 高速内存存储，TTL 自动过期，原子操作 |

**能不能只用一种？**

理论上可以，但不合理：
1. **只用 MySQL**：可以存所有数据，但缓存性能差（磁盘 IO），Checkpointer 需要额外适配
2. **只用 PostgreSQL**：可以替代 MySQL（PostgreSQL 功能更强），但缓存仍需要 Redis（内存 vs 磁盘性能差距 100x+）
3. **只用 Redis**：不适合持久化结构化数据，不支持复杂查询和事务

**最佳实践**：
- PostgreSQL 可以替代 MySQL（统一关系型数据库），减少运维成本
- Redis 不可替代（缓存场景性能差距太大）
- 本项目用 MySQL 可能是历史原因或团队偏好，迁移到 PostgreSQL 是合理的优化方向

## Q2: 本项目的 RAG 检索流程有哪些可以优化的地方？

**A:**

**当前流程**：
```
Query 改写 → 多查询并行检索 → 距离阈值过滤 → RRF 融合 → 重排序 → 缓存
```

**优化方向**：

### 1. 检索阶段
- **混合检索**：当前只有向量检索，可以加入关键词检索（BM25），互补提升召回
- **查询路由**：根据问题类型选择不同的检索策略（FAQ 用精确匹配，开放问题用语义检索）
- **元数据过滤**：检索前先按 category/source 过滤，减少噪声

### 2. 重排序阶段
- **本地重排序模型**：当前用在线 API（有延迟和成本），可以用本地 bge-reranker 模型
- **重排序缓存**：相同 query + docs 的重排序结果可以缓存

### 3. 缓存阶段
- **语义缓存**：当前是精确匹配缓存，可以用向量相似度做语义缓存（相似问题复用结果）
- **多级缓存**：本地缓存（进程内）+ Redis（分布式）+ 持久化（向量库）

### 4. 索引优化
- **增量索引**：当前是全量重建，可以支持增量更新
- **索引分区**：按 category 分区，检索时只查相关分区
- **HNSW 参数调优**：ef_construction、M 参数影响检索精度和速度

### 5. 文档处理
- **更智能的切分**：当前按字符切分，可以用语义切分（按段落/句子语义边界）
- **文档摘要**：长文档先生成摘要，检索时先匹配摘要再定位原文
- **元数据丰富**：添加更多元数据（创建时间、作者、标签），支持过滤

## Q3: 如何设计一个支持百万级用户的 AI 对话系统？本项目的架构需要做哪些改造？

**A:**

**当前架构瓶颈**：
1. **单实例 FastAPI**：无法水平扩展
2. **同步 LangGraph stream**：阻塞事件循环，并发能力有限
3. **MySQL 单库**：连接数和性能有上限
4. **Redis 单实例**：内存和连接数有限
5. **ChromaDB 本地持久化**：不支持分布式部署
6. **无消息队列**：高峰请求无法削峰

**改造方案**：

### 1. 应用层
- **多实例部署**：FastAPI 多 worker + 多实例，nginx 负载均衡
- **异步化**：LangGraph 改用异步图（agraph），或用 `asyncio.to_thread` 托管同步调用
- **连接池**：数据库连接池（SQLAlchemy pool、psycopg2 pool）
- **SSE 连接管理**：单机 SSE 连接数有限，需要 WebSocket 或消息推送替代

### 2. 数据层
- **MySQL 分库分表**：按 user_id 哈希分库，用户表水平拆分
- **读写分离**：主库写，从库读
- **PostgreSQL 连接池**：PgBouncer 中间件
- **Redis 集群**：Redis Cluster 或哨兵模式
- **向量库迁移**：ChromaDB → Milvus/Qdrant（分布式向量数据库）

### 3. 消息队列
- **引入 Kafka/RabbitMQ**：对话请求异步处理，削峰填谷
- **流式输出通过 WebSocket 推送**：SSE 不适合大规模并发

### 4. 缓存层
- **多级缓存**：CDN（静态资源）+ 本地缓存（进程内）+ Redis（分布式）
- **检索结果缓存**：语义缓存，相似问题复用
- **热点数据预热**：热门 FAQ 预加载到缓存

### 5. 可观测性
- **分布式追踪**：OpenTelemetry + Jaeger
- **指标监控**：Prometheus + Grafana
- **日志聚合**：ELK / Loki
- **告警系统**：异常率、延迟、错误码监控

### 6. 安全与限流
- **API 网关**：统一认证、限流、熔断
- **分布式限流**：Redis 滑动窗口限流
- **熔断降级**：LLM API 故障时降级到缓存或预设回答

## Q4: 本项目的用户自定义 system prompt 存在 MySQL，为什么不用 PostgresStore？

**A:**

**两种存储的对比**：

| 特性 | MySQL user_profile 表 | PostgresStore |
|------|----------------------|---------------|
| 数据结构 | 固定表结构，强 schema | 灵活 key-value，弱 schema |
| 查询方式 | SQL，支持复杂查询和索引 | namespace + key，简单查询 |
| 事务支持 | 完整 ACID | 有限 |
| 与用户表关联 | 容易（同库联表或同 user_id） | 需要额外维护关联 |
| LangGraph 集成 | 需要手动 CRUD | 原生支持 |
| 运维 | 已有 MySQL，无需额外 | 需要 Postgres（本项目已有） |

**选择 MySQL 的原因**：
1. **与用户信息强关联**：user_profile 和 userInfo 都是用户级数据，同库管理方便
2. **需要简单 CRUD**：用户自定义 prompt 就是简单的 key-value，不需要 Store 的复杂命名空间
3. **已有 MySQL 基础设施**：项目已经用 MySQL 存用户信息，不需要额外引入
4. **事务支持**：更新用户信息时可以事务保证一致性
5. **查询灵活**：可以按 theme、mcp_config 等字段筛选统计

**PostgresStore 更适合的场景**：
- LangGraph 自动管理的长期记忆（LLM 提取的用户画像、偏好）
- 需要灵活命名空间的层级数据
- 与 LangGraph 生态深度集成的场景

**本项目的分工**：
- MySQL user_profile：用户手动配置的信息（username、avatar、theme、mcp、自定义 prompt）
- PostgresStore：LLM 自动提取的长期记忆（对话中学习到的用户偏好）

## Q5: 如何设计一个支持插件化（MCP）的 AI 助手系统？

**A:**

**MCP（Model Context Protocol）架构设计**：

### 1. 核心概念
- **MCP Server**：外部工具提供者（如文件系统、数据库、API）
- **MCP Client**：AI 助手，连接 MCP Server 获取工具
- **MCP Host**：管理 MCP Server 生命周期和连接

### 2. 架构分层

```
┌─────────────────────────────────────────┐
│              AI 对话层                    │
│  LangGraph + LLM + 工具调用              │
└──────────────┬──────────────────────────┘
               │ 工具列表
┌──────────────▼──────────────────────────┐
│           MCP 客户端层                    │
│  - MCP Holder 管理（连接/断开/重连）     │
│  - 工具注册与发现                          │
│  - 工具调用代理                            │
└──────┬───────────────┬──────────────────┘
       │               │
┌──────▼──────┐ ┌──────▼──────┐
│ stdio Server │ │ sse Server   │
│ (本地进程)   │ │ (远程 HTTP)  │
└─────────────┘ └─────────────┘
```

### 3. 关键设计点

#### 3.1 配置管理
- 环境变量配置（本项目的 MCP_SERVERS JSON）
- 用户级配置（MySQL user_profile.mcp_config）
- 配置热更新（运行时动态加载/卸载 MCP Server）

#### 3.2 生命周期管理
- 启动时初始化 MCP Holders
- 健康检查（心跳检测，自动重连）
- 优雅关闭（关闭时释放子进程和连接）

#### 3.3 工具调用
- 工具列表注入 LangGraph
- 调用时参数校验（JSON Schema）
- 超时控制（避免 MCP Server 卡死影响主流程）
- 错误处理（MCP Server 故障时降级）

#### 3.4 安全隔离
- MCP Server 沙箱运行（限制文件系统访问、网络访问）
- 工具调用权限控制（用户只能调用授权的工具）
- 输入输出过滤（防止 prompt 注入）

### 4. 本项目的实现
- `load_mcp_server_configs()`：从环境变量加载配置
- `init_mcp_holders()`：初始化 MCP 客户端连接
- `mcp.http_app()`：挂载 MCP 服务器端点（供外部客户端调用）
- 工具列表传入 `chat_service.open(mcp_tools)`，注入 LangGraph

### 5. 可优化方向
- 用户级 MCP 动态加载（当前只支持全局配置）
- MCP Server 健康监控面板
- 工具调用审计日志
- MCP Server 市场（一键安装常用工具）

## Q6: 本项目的前端是单文件 Vue 3 SPA，如果项目规模扩大，应该如何演进？

**A:**

**单文件 SPA 的局限性**：
1. **代码体积膨胀**：所有 HTML/CSS/JS 在一个文件，超过 100KB 后维护困难
2. **组件无法复用**：没有组件化，重复代码多
3. **无构建优化**：没有代码分割、tree shaking、压缩
4. **开发体验差**：没有热更新、TypeScript、ESLint
5. **状态管理混乱**：ref 散落在 setup 中，复杂状态难以管理

**演进路径**：

### 阶段 1：模块化拆分（中小项目）
- 保留 Vue 3 CDN，但拆分 JS 为多个文件
- CSS 独立为文件
- 引入简单的状态管理（Pinia CDN 版）
- 优点：改动小，无需构建工具
- 缺点：仍有加载性能问题

### 阶段 2：Vite + 多组件（中大型项目）
- 迁移到 Vite 构建工具
- 组件化：每个功能拆为 `.vue` 单文件组件
- TypeScript 支持
- 路由：Vue Router
- 状态管理：Pinia
- UI 组件库：Element Plus / Ant Design Vue
- 优点：开发体验好，性能优化，可维护性强
- 缺点：需要构建部署流程

### 阶段 3：微前端（大型项目）
- 多个团队独立开发部署
- qiankun / wujie 微前端框架
- 共享基础组件和工具库
- 优点：团队自治，独立部署
- 缺点：架构复杂，通信成本高

**本项目的建议**：
- 当前规模（~100KB 单文件）适合阶段 1 或直接跳到阶段 2
- 如果预计功能会持续增加（更多页面、更多组件），建议尽早迁移到 Vite
- 迁移时可以渐进式：先搭建 Vite 项目骨架，再逐个迁移组件

## Q7: 如何设计一个支持多租户的 AI 对话系统？

**A:**

**多租户架构模式**：

### 1. 数据隔离方案

| 方案 | 隔离级别 | 成本 | 适用场景 |
|------|----------|------|----------|
| 独立数据库 | 物理隔离 | 高 | 大型企业客户，合规要求高 |
| 共享数据库，独立 Schema | 逻辑隔离 | 中 | 中型客户，需要数据隔离 |
| 共享数据库，共享表，tenant_id 字段 | 行级隔离 | 低 | 小型客户，SaaS 多租户 |

**本项目改造为多租户**：
- 选择**行级隔离**（共享表 + tenant_id），成本最低
- 所有业务表添加 `tenant_id` 字段
- 查询时自动过滤 `WHERE tenant_id = ?`
- 索引包含 `tenant_id`

### 2. 认证与授权
- 用户归属租户：user 表添加 tenant_id
- JWT 包含 tenant_id
- 资源归属校验：除了 user_id，还要校验 tenant_id
- 租户管理员角色：可以管理租户内用户

### 3. 配置隔离
- 每个租户独立的 system prompt
- 每个租户独立的知识库（向量库按 tenant_id 分区或独立 collection）
- 每个租户独立的 MCP 配置
- 每个租户独立的主题/品牌定制

### 4. 资源配额
- 每个租户的 API 调用次数限制
- 每个租户的用户数限制
- 每个租户的存储空间限制
- 超限告警和自动限流

### 5. 向量库多租户
- **方案 A**：每个租户独立 collection（隔离好，但 collection 数量有上限）
- **方案 B**：共享 collection，metadata 加 tenant_id，检索时过滤（简单，但需要确保过滤生效）
- **方案 C**：独立向量库实例（隔离最好，成本高）

### 6. 本项目的改造点
- userInfo 表添加 tenant_id
- user_profile、user_files 表添加 tenant_id
- ChromaDB collection 的 metadata 添加 tenant_id，检索时过滤
- JWT payload 添加 tenant_id
- `require_self_or_admin` 依赖增加 tenant 校验
- 新增租户管理接口（租户管理员 CRUD 用户）

## Q8: 本项目的对话历史存在 PostgresSaver，如果需要导出或迁移对话历史，如何设计？

**A:**

**PostgresSaver 数据结构**：
- `checkpoints` 表：图状态快照（thread_id, checkpoint_id, metadata, checkpoint blob）
- `checkpoint_blobs` 表：大状态数据
- `checkpoint_writes` 表：中间写入记录

**导出方案**：

### 1. API 导出
- 新增导出接口：`GET /api/users/{user_id}/export`
- 支持格式：JSON、Markdown、PDF
- 支持筛选：时间范围、会话 ID
- 异步导出（大数据量时后台任务，完成后通知）

### 2. 数据格式设计
```json
{
  "export_version": "1.0",
  "export_time": "2026-08-21T10:00:00Z",
  "user_id": "123",
  "sessions": [
    {
      "thread_id": "abc",
      "title": "对话标题",
      "created_at": "2026-08-20T10:00:00Z",
      "messages": [
        {"role": "user", "content": "问题", "timestamp": "..."},
        {"role": "assistant", "content": "回答", "timestamp": "..."}
      ]
    }
  ]
}
```

### 3. 从 PostgresSaver 提取消息
- PostgresSaver 存储的是图状态快照，不是直接的消息列表
- 需要从 checkpoint 中解析 messages 字段
- 可以用 `graph.get_state(config)` 获取最新状态
- 遍历 checkpoint 历史提取完整对话

### 4. 迁移方案
- **同数据库迁移**：SQL 导出导入，注意 thread_id 唯一性
- **跨数据库迁移**：API 导出 + API 导入，格式中立
- **向量库迁移**：ChromaDB 数据导出为 JSON（id, document, metadata, embedding），再导入新库

### 5. 本项目的实现建议
- 新增 `export_service.py`：封装导出逻辑
- 导出接口支持流式下载（大文件不占内存）
- 导入接口支持幂等（相同 thread_id 不重复导入）
- 导出时包含用户配置（profile、theme、mcp）

## Q9: 如何评估一个 RAG 系统的效果？有哪些评估指标？

**A:**

### 1. 检索质量指标

| 指标 | 含义 | 计算方式 |
|------|------|----------|
| Recall@K | 前 K 条结果中相关文档的比例 | 相关文档在前K条的数量 / 总相关文档数 |
| Precision@K | 前 K 条结果中相关文档的比例 | 相关文档在前K条的数量 / K |
| MRR | 第一个相关文档的排名倒数 | 1 / rank_of_first_relevant |
| NDCG@K | 归一化折损累计增益 | 考虑相关性等级和排名的加权指标 |
| Hit Rate | 至少有一个相关文档的查询比例 | 有相关结果的查询数 / 总查询数 |

### 2. 端到端回答质量指标

| 指标 | 含义 | 方法 |
|------|------|------|
| 回答相关性 | 回答是否解决了用户问题 | 人工评估 / LLM-as-Judge |
| 事实准确性 | 回答是否有幻觉 | 与检索文档对比 / 事实核查 |
| 引用准确性 | 回答是否正确引用了来源 | 检查引用的文档是否支持回答 |
| 完整性 | 回答是否覆盖了问题的所有方面 | 人工评估 / LLM 评估 |
| 流畅性 | 回答是否自然流畅 | 人工评估 / 语言模型评分 |

### 3. 性能指标

| 指标 | 含义 | 目标 |
|------|------|------|
| 首 token 延迟 (TTFT) | 从请求到第一个 token 的时间 | < 1s |
| 总延迟 | 从请求到回答完成的时间 | < 10s |
| 吞吐量 | 每秒处理的请求数 | 根据业务需求 |
| 检索延迟 | 向量检索 + 重排序的时间 | < 500ms |
| 缓存命中率 | 检索缓存命中的比例 | > 30% |

### 4. 评估方法

#### 4.1 离线评估
- 构建测试集：问题 + 相关文档 + 标准回答
- 自动计算检索指标（Recall@K、MRR、NDCG）
- LLM-as-Judge 评估回答质量
- 批量测试，对比不同配置的效果

#### 4.2 在线评估
- A/B 测试：不同检索策略对比
- 用户反馈：点赞/点踩、重新提问率
- 业务指标：对话完成率、用户满意度

#### 4.3 人工评估
- 抽样人工标注回答质量
- 建立评估标准和评分细则
- 多人标注，计算标注一致性（Cohen's Kappa）

### 5. 本项目的评估建议
- 构建 50-100 条测试问答对（覆盖 FAQ、开放问题、边界情况）
- 用脚本自动计算 Recall@10、MRR、NDCG@10
- 用 DeepSeek 作为 LLM Judge 评估回答相关性和事实准确性
- 监控线上 TTFT、总延迟、缓存命中率
- 定期回归测试，确保优化不降低效果

## Q10: 如果 LLM API 调用失败或超时，本项目应该如何设计容错和降级机制？

**A:**

### 1. 故障场景分析

| 故障场景 | 影响 | 频率 |
|----------|------|------|
| API 超时 | 对话卡住，用户等待 | 中 |
| API 限流 (429) | 请求被拒绝 | 中 |
| API 密钥失效 | 所有请求失败 | 低 |
| API 服务不可用 | 所有请求失败 | 低 |
| 网络波动 | 部分请求失败 | 高 |
| 模型返回格式错误 | 解析失败 | 低 |

### 2. 容错机制设计

#### 2.1 重试机制
- **指数退避重试**：失败后等待 1s、2s、4s 重试，最多 3 次
- **只对可重试错误重试**：超时、5xx、网络错误；不重试 4xx（参数错误）
- **抖动（Jitter）**：退避时间加随机偏移，避免雪崩
- **实现**：tenacity 库或自定义装饰器

```python
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=1, max=10),
    retry=retry_if_exception_type((TimeoutError, APIError)),
)
def call_llm(prompt):
    return model.invoke(prompt)
```

#### 2.2 超时控制
- 每个 API 调用设置超时（如 30s）
- 流式输出设置首 token 超时（如 10s）和总超时（如 120s）
- 超时后返回友好提示，不无限等待

#### 2.3 降级策略
- **缓存降级**：返回最近一次相似问题的缓存结果
- **简化回答**：跳过 RAG 检索，直接用 LLM 回答（可能不准确但能响应）
- **预设回答**：返回预设的友好提示（"服务暂时不可用，请稍后重试"）
- **备用模型**：主模型故障时切换到备用模型（如 DeepSeek → 混元）

#### 2.4 熔断机制
- 统计错误率，超过阈值（如 50%）时熔断
- 熔断期间直接返回降级结果，不调用 API
- 半开状态：定期尝试少量请求，恢复后关闭熔断
- 实现：pybreaker 库

#### 2.5 队列缓冲
- 高峰请求放入消息队列（Kafka/RabbitMQ）
- 消费者按 API 速率限制处理
- 用户可以稍后查看结果（异步模式）

### 3. 本项目的改造点

#### 3.1 LLM 调用层
- 封装 `LLMService`，统一处理重试、超时、熔断
- 支持多模型配置（主模型 + 备用模型）
- 调用日志和指标收集

#### 3.2 检索层
- 向量检索失败时降级为关键词检索
- 重排序 API 失败时跳过重排序，用检索原始排序
- 检索缓存延长 TTL，故障时更多命中缓存

#### 3.3 API 层
- 对话接口增加超时返回（超时后返回已生成的部分内容）
- 健康检查接口检测下游服务状态
- 错误响应包含重试建议（"服务繁忙，请 10 秒后重试"）

#### 3.4 前端
- 网络错误时显示友好提示，不白屏
- 支持重新发送（保留用户输入）
- 显示服务状态（正常/繁忙/不可用）

### 4. 监控与告警
- API 调用成功率、延迟、错误码分布
- 熔断状态监控
- 降级触发次数
- 异常率超过阈值时告警（邮件/短信/钉钉）
