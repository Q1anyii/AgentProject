## 一、类封装设计

### 现状的三个问题

1. `client`/`collection` 是**模块级全局**（[graph.py](file:///E:/工作文件/AgentProject/src/graph.py#L23-L27)），与实例生命周期解耦，测试/多实例场景难处理
2. `build_chat_graph()` 每次调用都**重新创建连接池 + 重新定义 5 个节点函数 + 3 个 prompt + 建表 + compile**，返回 `(graph, pool)` 后 pool 生命周期要调用方自己管
3. `InMemoryCache` 在函数内创建，**不在 lifespan 掌控内**（guide 第 5 行明确要求移到 lifespan）

### 目标结构

```
ChatService（类，收拢全部资源与业务方法）
│
├── __init__()                    # 只存配置（.env 的 DB URL），不建任何重资源
│
├── open()  ←→  close()           # 幂等；对应 FastAPI lifespan 的启动/关闭
│   ├── chroma client + collection          ← 原模块级单例收进来
│   ├── ConnectionPool + setup()            ← 原 build_chat_graph 内逻辑
│   ├── PostgresSaver / PostgresStore       ← 共用 pool
│   ├── InMemoryCache()                     ← 实例级，随 open/close 同生命周期
│   └── _build_rerank_graph() / 主图 compile（只 build 一次）
│
├── 业务方法（main.py 端点的全部逻辑收编）
│   ├── invoke(user_id, thread_id, input_str) -> str   # config 组装 + invoke + 取末条
│   ├── a_invoke(...)                                  # asyncio.to_thread(invoke)
│   ├── get_history(thread_id) / list_sessions(user_id)
│   ├── get_memory(user_id) / delete_session(thread_id)
│   └── 属性暴露: .graph / .pool / .collection（端点特殊场景兜底）
│
└── 模块级工厂 get_chat_service()   # 或直接由 lifespan new + open/close
```


### 三个关键决策

| 决策点 | 建议 | 理由 |
|---|---|---|
| 节点函数怎么放 | **保持闭包不动**，`_build_*` 内部通过参数注入 `self.collection` | 纯搬移零风险，图逻辑一行不改；以后要单测再提为类方法 |
| 懒加载还是急加载 | **open() 放 lifespan 启动阶段**（建库表、compile 全做） | 数据库故障启动即暴露，不拖到首个请求才 500 |
| 单例怎么实现 | 去掉 `@lru_cache`，缓存职责由 service 单例接管（open 只 build 一次） | `query_rerank_graph` 的 lru_cache 语义与类实例重复 |

### main.py 的对应变化

- lifespan 变成 `service = ChatService(); service.open()` → yield → `service.close()`
- 端点瘦身为"解析参数 → 调 service 方法 → 组装响应"；现在每个端点里现写的 `PostgresSaver(pool)` 临时实例全部收进 service（[main.py](file:///E:/工作文件/AgentProject/src/main.py#L84-L130) 的 memory/sessions/delete 三处重复代码消失）

### ⑤ 流式的实现思路（核心）

```
async def chat_stream(...) 端点（原 /api/chat 升级）
└── StreamingResponse(gen(), media_type="text/event-stream")
    └── async def gen():
        ├── async for (chunk, meta) in graph.astream(config, stream_mode="messages"):
        │   └── 每个 chunk 是 AIMessageChunk → yield "data: {json}\n\n"
        └── 结束后 yield "data: [DONE]\n\n"
```


三个关键点：

1. **直接 `await graph.astream(...)`**：langgraph 1.x 对同步 checkpointer 会自动内部线程化，不用自己包 to_thread——比把 `graph.stream` 包进异步生成器更省事（guide 说的"包装进异步生成器"就是这个语义）
2. **nginx 是最大坑**：SSE 长连接默认被 nginx 缓冲成块输出，token 变"一坨一坨"——必须 `location /api/ { proxy_buffering off; }`（或后端返回 `X-Accel-Buffering: no` 头），否则流式白做
3. **前端配合**：`EventSource` 不支持 POST，必须 `fetch` + `ReadableStream` 手写 SSE 解析；建议做降级——流式失败自动退回整段返回

### 其他 guide 细节

- **thread_id**（第 7 行）：建议后端 `uuid4()` 生成兜底（当前前端传 `thread_xxx`，可接受；v2 改为后端生成防伪造、防串记忆）
- **多 worker**（第 10 行）：无需任何处理——连接池/cache 各进程独立，chroma SQLite WAL 多进程读安全，你的只读场景没问题
- **Supervisor 多 Agent 模式**（19-44 行）：架构演进方向，你的 `classify_node` + `route` 已经是"意图识别 + 路由"的雏形，将来可拆成 Supervisor + IntentAgent/RAGAgent/MemoryAgent；与本次类封装不冲突，类封装反而为它提供了干净的挂载点（每个 Agent 一个 service 方法）

4. 同步 vs 异步、并发
PostgresSaver / PostgresStore / graph.invoke 都是同步实现。最省事的做法：路由用普通 def 端点，FastAPI 会自动放进线程池执行，不会阻塞事件循环——第一版强烈建议这条路，正确性优先
若后续要流式，再升级为 async def + StreamingResponse（SSE 逐 token 输出），内部用 graph.stream(stream_mode="messages") 包装进异步生成器
并发安全无需额外处理：连接池自带多线程复用，PostgresSaver/PostgresStore 内部有锁，chroma client 查询线程安全，InMemoryCache 有锁保护——都是现成的
注意 InMemoryCache 目前是模块级单例，抽到 graph.py 后在 lifespan 中创建实例即可
5. 需要处理的细节
thread_id 生成：uuid4()，避免多个请求互相串记忆
CORS：若前端独立部署（Vue/React），加 CORSMiddleware
错误处理：LLM 调用失败、检索异常等统一捕获，返回结构化错误（如 500 + {"detail": "..."}），loguru 日志照常
多 worker 部署：uvicorn 多进程时，内存 cache、连接池各进程独立（无共享冲突）；chroma 的 SQLite 在 WAL 模式下多进程并发读安全，本项目只读场景没问题
6. 可选进阶（后续再考虑）
SSE 流式回答：体验更好，接口不变，响应变流
鉴权：user_id 从 JWT/会话解析，杜绝客户端伪造
LangServe 对比：langgraph 官方 langserve 包可直接把图暴露为 REST + playground，开箱即用但定制性弱（如历史/记忆查询端点还得自己写）；你的场景需要自定义端点，手写 FastAPI 更合适

建议的改造顺序：① 抽 graph.py（纯搬移，不动逻辑）→ ② 写 main.py 的 lifespan + /api/chat + /health（跑通最小闭环）→ ③ 补 history / memory / delete 端点 → ④ 加 CORS、错误处理、日志 → ⑤ 可选流式。
